# Findings — build 1, 2026-08-31

Corpus, extraction and alignment described in `PIPELINE.md`. Numbers below come
from `REPORT.txt` (generated by `analyze.py features_v2.jsonl`).

---

## 1. The Tier-2 gate is already most of a classifier

`MEASURE()` refuses to return a feature vector when no block of ≥75 alignment
columns exists in which copies are both present and agreeing. That refusal is a
verdict, and on its own it separates almost everything:

| class | sets | abort rate |
|---|---|---|
| POS (curated subfamilies) | 28 | **4 %** |
| NEGJITTER (edges displaced ±20–100 bp) | 28 | 4 % |
| NEGSPLICE (chimeras) | 20 | 15 % |
| MIXED10 (10 % random loci) | 28 | 57 % |
| NEGTRUNC5 (5′-truncated) | 28 | 68 % |
| MIXED30 (30 % random loci) | 28 | **86 %** |
| NEGRAND (pure random loci) | 20 | **95 %** |

Every feature table below is conditioned on surviving this gate, so it is
measured on the hardest, most family-like negatives only.

## 2. The spec's own question about contamination, answered

§3 asked for "the contamination level at which the consensus edge blurs", to set
the pruning threshold. Measured: **10 % random-locus contamination already
destroys the consensus anchor in 57 % of sets, and 30 % in 86 %.** The pruning
loop therefore cannot rely on getting a feature vector out of a contaminated set
at all — it has to prune on something that survives the anchor failing. This
argues for making `core_too_short` a first-class `REVIEW`/`MIXED` verdict rather
than an error, which is the answer to the §7 open item about whether MIXED
should be a third class: it must be, because the gate produces it before any
model runs.

## 3. `rank1_frac` needs the null; `rank1_excess` is the real statistic

Raw `rank1_frac` is saturated — 0.992 in real families, 0.977–0.989 in every
negative — because a copy × window identity matrix is near-rank-1 by
construction at these dimensions. Against MIXED it reaches only AUC 0.67.

Subtracting a permutation null (independent row shuffling within each window
column, which preserves every column's marginal exactly and destroys only
per-copy coherence) gives `rank1_excess`, and that **separates MIXED perfectly,
AUC = 0.000 in both directions**: POS median 0.0011, MIXED10 0.0172, MIXED30
0.0345.

This is not a core-width artifact. Within real families `corr(core_cols,
rank1_excess) = −0.29`, so narrow cores do inflate it slightly — but real
families restricted to the MIXED sets' own core width (60–130 columns, n = 75)
still sit at 0.0019 against 0.0182 for MIXED at width 90. A tenfold gap at
matched width.

**Recommendation: replace `rank1_frac` with `rank1_excess` in the spec.** The
null is cheap (60 SVDs of a 100 × 50 matrix) and without it the statistic is
close to useless.

## 4. `cliff_z` is sample-size dependent and cannot be thresholded as written

The side quest was decisive here. In all five families `cliff_z` falls
monotonically as n grows:

| family | n=25 | n=50 | n=100 | n=200 |
|---|---|---|---|---|
| ccr/g3 | 7.18 | 6.06 | 4.95 | 4.37 |
| saq/s1 | 6.69 | 6.34 | 5.49 | 5.08 |
| saq/s5 | 9.64 | 8.73 | 7.97 | 7.29 |
| saq/s7g | 6.88 | 6.82 | 5.62 | 5.02 |
| teu/t5 | 5.72 | 5.12 | 4.83 | 4.68 |

`corr(n_copies, cliff_z) = −0.34` overall. A fixed threshold on `cliff_z` would
mean different things at n = 25 and n = 200 — and would silently favour smaller
samples. Either fix n in the protocol or normalise. `cliff` itself (the raw
core-minus-flank contrast) is stable and moves the other way (+0.03 to +0.07
from n=25 to n=200), so it is the safer quantity of the two.

## 5. The consensus anchor lands where the copies say it should — but is not reproducible

Two separate results, and they point in opposite directions.

**Good:** `resL_bias = −2` and `resR_bias = +3` alignment columns in real
families. The consensus-IC anchor sits within a few columns of the median
per-copy edge, and the per-copy residual spread is tight (`resL_spread` median
10 columns, IQR 10). This directly supports the spec's demotion of per-copy
breakpoints from boundary-*setting* to boundary-*testing*: the consensus edge is
the right anchor.

**Bad, and this is the build's main negative result:** across K = 20 independent
subsets of the *same* family, `core_cols` has a standard deviation of 50–95
columns at **every** n from 25 to 200, with no downward trend. Two random
subsets of the same family routinely disagree about the element's width by more
than 25 %.

So the §3 side quest does *not* yield an n_min, because sample size is not what
limits reproducibility here — the anchor rule itself is. Concretely, `anchorL`
and `anchorR` come from a single crossing of a smoothed profile at a level set
0.35 of the way from background to the 90th percentile; where a core has
internal low-conservation segments, that crossing jumps between the true edge
and an internal dip.

**This blocks the spec's §6 step 1.** The boundary rule cannot be validated
against manual calls until it is stable against resampling. Suggested fix before
anything else: replace the single crossing with a change-point fit (or require
the crossing to persist over a run of ≥ 50 columns), then re-run the side quest
unchanged — the harness is built and re-running costs about twenty minutes.

## 6. Two bugs in the obvious implementation, worth recording

Both silently produced plausible-looking output rather than failing.

1. **Scoring per-copy identity over all columns inverts the cliff.** MAFFT
   spreads 100 non-homologous flanks over ~1200 columns, so the majority symbol
   in the flank is a gap and every copy "agrees" with it ~92 % of the time. The
   first run reported `core_identity = flank_bg = 0.92`, `cliff = 0.0` for
   genuine families. Identity must be scored only over columns where the copy
   itself carries a base. After the fix: core 0.905, flank 0.500, cliff 0.402.
2. **`np.convolve` smears NaN across the whole kernel.** One absent window wipes
   out a copy's entire smoothed profile, so per-copy edges silently vanished —
   `resL_spread` read 126 columns instead of 10.

## 7. Things that did not work, stated as such

- **`tsd_frac` is not functional.** It reports 0.01 in real families and 0.00–0.04
  in negatives, i.e. noise. Tal SINEs should carry TSDs. The detector searches for
  an exact direct repeat within 30 bp of each copy's own edges, and the edges are
  only known to 5-column window resolution. Do not read the current numbers as
  evidence about TSDs either way.
- **Tier 3 / mosaicism is untested, not disproven.** `NEGSPLICE` mostly survives
  the gate with a high `cliff_z` (5.49, i.e. above POS), and neither
  `rank2_frac` nor `rank1_excess` flags it (AUC ≈ 0.55). But the negative is
  mis-designed: every chimera splices at the same relative midpoint, so the
  result is a coherent new family, not a mosaic. A proper test needs breakpoints
  that vary per copy so different copy subsets carry different blocks. The
  spec's SVD idea has not actually been challenged yet.
- **`frac_aligned` shows AUC 1.000 vs NEGTRUNC5 and 0.007 vs NEGSPLICE.** Treat
  as an artifact of total alignment width, not a discovery — both those classes
  are built by concatenating foreign sequence, which changes alignment geometry
  directly. It should be dropped rather than trusted.
- **`NEGJITTER` is not a negative.** Displacing every copy's edges by ±20–100 bp
  changes essentially nothing: 4 % abort rate (same as POS), `cliff_z` 5.18 vs
  4.97, `core_cols` 202 vs 219. That is a genuine and useful robustness result —
  the anchor recovers the true element from a badly centred extraction — but the
  class should be relabelled a control, and it means the corpus currently has no
  negative that tests boundary-shift sensitivity.
- **`res_asymmetry` and `resR_bimod` separate nothing** (|AUC−0.5| < 0.12
  everywhere). The spec expects `res_asymmetry` to catch LINE-like ragged 5′
  edges; on NEGTRUNC5 it reads 0.000 against POS 0.309. `len_cv` catches that
  class perfectly instead (AUC 0.000, median 0.094 vs 0.020).

## 8. What the feature set looks like now

Surviving, validated, non-redundant (no pair exceeds |r| > 0.9):

| feature | what it catches | evidence |
|---|---|---|
| gate: `core_too_short` | random loci, heavy contamination, truncation | 95 / 86 / 68 % abort |
| `rank1_excess` | contamination | AUC 0.000 vs MIXED10 and MIXED30 |
| `len_cv` | 5′ truncation, length heterogeneity | AUC 0.000 vs NEGTRUNC5 |
| `cliff` | boundary existence | AUC 0.80 / 0.89 vs MIXED, n-stable |
| `sharp_R` | boundary sharpness | AUC 0.92 / 0.95 vs MIXED |
| `ic_contrast` | boundary existence | AUC 0.99 vs MIXED30, 1.00 vs NEGTRUNC5 |
| `resL_spread`, `resR_spread` | per-copy edge coherence | POS median 10–11 columns |

Not yet usable: `tsd_frac`, `res_asymmetry`, `resR_bimod`, `frac_aligned`,
`rank1_frac` (use `rank1_excess`), `cliff_z` (until n-normalised).

## 9. Next, in order

1. Stabilise the anchor (§5) and re-run the side quest. Nothing else is worth
   tuning while two subsets of one family disagree by 25 % on element width.
2. Rebuild `NEGSPLICE` with per-copy-varying breakpoints and re-test the SVD —
   this is the only way to find out whether the spec's central Tier-3 idea works.
3. Fix or drop `tsd_frac`; it is currently reporting noise under a meaningful name.
4. Add the natural negatives still missing: LINEs (candidates exist at
   `teu/line/` on KIT), satellites, processed pseudogenes. All present negatives
   except NEGRAND are synthetic.
5. Only then fit anything. The gate plus three features already does most of the
   work, and a model fitted now would be fitted to an unstable anchor.

## 10. Correction and prior art — after reading the repo's LOG.md files (added same day)

The first pass read `WORKFLOW.md` only. The six per-species `LOG.md` files were
not opened, and they change two things.

**Correction.** "The published alignments are element-only" holds for the
subfamily alignments (`top100` / `rand100` / `subfam`), which is what was
sampled. It is not true of the repo generally: the **tribe** alignments carry
50 bp left + 70 bp right of real flank, per `*/tribes/tribes_metadata.txt` and
confirmed by measurement (266 bp locus, 386 bp ungapped). The rebuild remains
correct — 50+70 is far short of 300, and tribes are a `vsearch --id 0.99`
de-novo clustering of the youngest near-identical copies, which §2 of the spec
warns are the least informative — but the stated reason was overgeneralised.

**Prior art that duplicates, and improves on, section E of this build.**
`eri/LOG.md` (2026-08-21) already implements flank-uniqueness testing:

- True background established empirically: 2 000 pairs from 300 random unrelated
  70 bp genomic windows → **25.0 % mean pairwise identity**, matching the
  theoretical value for independent 4-letter DNA. Uniqueness threshold set at
  ≤ 35 % on both flanks.
- A recorded failure worth not repeating: the first version tested for
  *exact-duplicate* flanks only, and passed cluster `11535`, which actually has
  66.5 % mean pairwise right-flank identity with a visible shared motif.
- Calibration in hand: contaminated clusters 0–1.8 % singleton-flank, clean ones
  60–82 %.

**This exposes a defect in `measure.py`.** `pairwise_identity()` runs on the
MAFFT alignment, over columns where both copies are non-gap — so the aligner has
already co-located the similar segments, and the value is inflated. Measured
`flank_bg` 0.500 and `flank_med_L` 0.475 against a true background of 0.25.
Consequences:

1. Tier 2's "collapse to genomic background" is being scored against a floor
   about twice the real one. `cliff` is still an internally consistent contrast,
   but it is not the quantity the spec describes.
2. `nested_frac_L` / `nested_frac_R` thresholds (`mx > max(0.75, med + 0.25)`)
   are calibrated in the wrong units, which probably explains the implausible
   0.87 for dmo/d5.
3. Unexplained and blocking for that feature: POS flanks read 0.475 while
   NEGRAND flanks read 0.317. Real SINE flanks should not be *more* similar to
   each other than random loci are. Candidate explanations — the A-rich
   insertion signature and poly-A tail bleed that the spec explicitly expects,
   or a conservative anchor leaving element edges inside the flank window — but
   this must be resolved before `nested_frac` is used for anything.

Fix: compute flank identity on ungapped sequence, and calibrate against random
same-length genomic windows from the same genome, as `eri/LOG.md` does.

**Bearing on spec §F.** `eri/LOG.md` tested periodicity in SINE-hit spacing as a
satellite proxy — essentially the spec's `coord_cluster` — against direct TRF
tandem annotation, and found it unreliable: wrong on four of ten tribes in both
directions. A cluster can sit mostly inside satellite DNA with irregular
spacing, or have regular spacing while lying outside any TRF region. Direct
intersection with tandem annotation was the reliable check. §F's
`coord_cluster` should be treated as a question-raiser, not an answer.

## 11. Section 5 retracted — the boundary rule was never the problem (same day)

Two corrections from the author, both confirmed by measurement. Section 5's
"blocker" was an artifact of this build's implementation.

**11a. 300 bp flanks degrade the alignment.** The spec says widening to 300 bp
"costs nothing". Measured, it costs the alignment: MAFFT must align 600 bp of
unrelated DNA per copy and invents thousands of junk columns. A ~250 bp element
ends up smeared across 1200-1475 alignment columns — a 4-6x dilution — and the
dilution grows with copy number, which is precisely why the called width drifted
with n. Cutting flanks to 70 bp took the median alignment from 3025 columns to
942. The background identity never needed to be in the alignment at all; it is
measured from random genomic windows, as `eri/LOG.md` does.

**11b. Anchor on the known consensus, added as a row.** Not a consensus derived
from the alignment — the pre-existing subfamily consensus from
`results/consensuses.fa`, aligned in alongside the copies. Its first and last
nucleotide delimit the element. No threshold, no smoothing, no free parameter,
and nothing that moves when the copies are resampled. This is already the site's
own convention: `saq_s1_30seqs_rand100.aln.fa` carries `>s1_30seqs` as row 1.

One subtlety: the consensus row's *span in columns* is not the readout — copies'
insertions stretch it from 1.2x its true length at n=25 to 3.9x at n=200. The
readout is each copy's ungapped base count between the consensus's first and
last nucleotide, i.e. the element length of that copy.

**Reproducibility, same side quest, same alignments:**

| boundary rule | SD of element length across K=20 subsets |
|---|---|
| profile crossing (section 5) | 74.2 |
| count of columns with occupancy > 0.9 | 13.3 |
| **known consensus row, 70 bp flanks** | **10.7 bp** |

Several family/n cells reach 0.5-1.1 bp. The absolute values are right
(250-280 bp, matching the Tal consensus lengths) and no longer drift with n
(ccr/g3 265→259 from n=25 to n=200; saq/s5 250→248).

**It also yields a discriminator for free** — the within-set CV of per-copy
element length: real families 0.052, MIXED10 0.107, MIXED30 0.144, NEGRAND
0.180, NEGTRUNC5 0.271. NEGSPLICE stays at 0.062, consistent with §7's note that
that negative is mis-designed.

**Consequences for the earlier sections.** §5's "this blocks §6 step 1" is
withdrawn — the boundary rule is reproducible once anchored properly. §4's
n-dependence of `cliff_z` and §10's inflated flank background both share the
same root cause as §5 (over-long flanks distorting the alignment) and must be
re-measured on `aln_c/` before anything in §3, §4 or §8 is trusted. The corpus
is rebuilt and aligned at `/data/W/toki/SINE_disc/aln_c/` and locally in
`aln_c/`; `measure.py` still reads the old geometry and needs porting to the
consensus anchor.
